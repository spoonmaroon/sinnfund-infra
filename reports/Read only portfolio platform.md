# Precompute Returns, Then Render Portfolios Instantly

**Keep the existing FastAPI portfolio service, make it an instant read-only view over precomputed data, and add Chart.js rather than adopting a full portfolio application.** The current page has no deliberate animation: it waits for compressed Flex files to be found, decompressed, parsed, serialized into a large inline payload and, on the live route, repriced through two sequential local calls before the browser rebuilds the entire table. Production was fast on the server during the November 6, 2026 inspection, but each response still carried nearly a megabyte and hundreds of positions plus tax lots that the first screen did not need. The first release should instead show a compact account summary and a cumulative-return chart immediately from the last validated artifact, then load positions and lots only after a user opens an account. The existing Flex credential can request historical date ranges, but **the token does not calculate returns and the current saved query omits the NAV, date, currency and TWR fields required to calculate them faithfully**. Create a separate versioned `returns-v1` Flex Query, validate its shape, perform one resumable backfill, and update it once daily thereafter. Keep all browser-facing routes GET-only behind shared institutional authentication; the screenshot motivates an account-summary-first layout, but it contains no historical series and therefore cannot source or validate the chart.

## Four stages turn the current page into an instant dashboard

**Verified current production facts.** Neither checked-in portfolio page contains animation rules, delayed timers or an animation loop; each embeds the full portfolio JSON in the HTML and calls one synchronous render routine ([close dashboard source](https://github.com/SinnQuant/sinnfund-infra/blob/main/services/flex-web/web.py), [live dashboard source](https://github.com/SinnQuant/sinnfund-infra/blob/main/services/flex-web-live/web-live.py)). Every request reparses the latest compressed Flex archives and returns `Cache-Control: no-store`; the live route also makes sequential local price and health requests with five-second timeouts, creating a degraded-path delay of roughly ten seconds before first byte ([live parser](https://github.com/SinnQuant/sinnfund-infra/blob/main/services/flex-web-live/parse_flex_positions_live.py), [live route](https://github.com/SinnQuant/sinnfund-infra/blob/main/services/flex-web-live/web-live.py)). A read-only production measurement on November 6 found 403 summary positions and 943 lots across 21 accounts; generated responses were roughly 835–925 KB, while localhost time to first byte was only 60–127 ms ([deployed applications](ssh://sinnfund/opt/), [deployed archive](ssh://sinnfund/var/lib/flex-ingest/flex/data/20261105/)). This means the immediate complaint is best addressed by removing request-time dependencies and reducing transfer, parse and DOM work; no animation needs tuning. The [attached screenshot](file:///var/folders/5j/8x8xvxqd38g0zg0s85jqhzvr0000gn/T/codex-clipboard-14c7c57d-1ce5-4c9d-8352-88753ec76a08.png) is useful product direction because it leads with one row per account, NAV, allocation and return, but **it is a presentation reference, not historical evidence**.

This staged design follows the repository’s existing rule that raw compressed Flex XML is immutable evidence and downstream projections must be reproducible ([ADR-0007](https://github.com/SinnQuant/sinnfund-infra/blob/main/docs/decisions/0007-archive-raw-flex-xml.md)). It also preserves the deliberate separation between public read-only reporting and private controls ([ADR-0005](https://github.com/SinnQuant/sinnfund-infra/blob/main/docs/decisions/0005-separate-public-read-only-and-private-controls.md)). SQLite is enough for the normalized history at this scale: a unique daily record keyed by `(scope_key, account_key, date)` should carry NAV, base currency, external flow, daily TWR, source checksum/query version and quality status; a source-import table should make retries idempotent. A managed database, WebSocket stream and frontend framework add no value to this first release.

## A new Flex query unlocks defensible returns

**Official IBKR capability.** A Flex token authenticates requests; the saved Query ID defines accounts, sections, fields and format. The caller can override the saved period with `fd`/`td`, but IBKR limits a request to 365 days and limits the token to one request per second and ten requests per minute ([Flex Web Service configuration](https://ibkrguides.com/orgportal/performanceandstatements/flex3.htm), [rate-limit and error reference](https://www.ibkrguides.com/adminportal/performanceandstatements/flex3error.htm)). IBKR says Flex data is available for the current calendar year plus the four previous calendar years, so **ALL means “since the earliest complete Flex record,” not necessarily true inception** ([Flex Queries](https://www.ibkrguides.com/orgportal/performanceandstatements/flex.htm)). The currently archived production history spans only October 9 through November 5, 2026, and the recent NAV-summary rows contain only an account identifier; no report date, total NAV, base currency, Change in NAV or TWR is present ([deployed archives](ssh://sinnfund/var/lib/flex-ingest/flex/data/)). Cash and positions cannot repair this: ending cash is not total NAV, and current holdings cannot reconstruct historical performance after trades, transfers, fees, FX and corporate actions ([existing NAV incident](https://github.com/SinnQuant/sinnfund-infra/blob/main/docs/incidents/0007-ibkr-flex-archives-missing-official-nav.md)).

The dedicated **saved Activity Flex Query must use XML output and select only these fields**. In **Account Information**, select `Account ID`, `Account Alias`, `Currency`, `Date Opened`, `Date Closed` and `Date Funded`; omit names, addresses, email, birth date and every other personal field. In **Change in NAV**, select `Account ID`, `Account Alias`, `From Date`, `To Date`, `Starting Value`, `Deposits/Withdrawals`, `Internal Cash Transfers`, `Asset Transfers`, `Dividends`, `Withholding Tax`, `Change in Dividend Accruals`, `Interest`, `Change in Interest Accruals`, `Advisor Fees`, `Client Fees`, `Other Fees`, `Commissions`, `Transaction Tax`, `Forex Translation`, `Linking Adjustments`, `Other`, `Ending Value` and `TWR`; use the Mark-to-Market mode and include `Mark-to-Market` as a reconciliation field. IBKR defines TWR here as return independent of contribution and withdrawal timing ([Change in NAV field reference](https://ibkrguides.com/reportingreference/reportguide/changeinnav_fq.htm)). In **Net Asset Value Summary in Base**, select `Account ID`, `Account Alias`, `Report Date`, `Cash`, `Stock`, `Options`, `Commodities`, `Bonds`, `Interest Accruals`, `Dividend Accruals` and `Total`; the essential publication fields are `Report Date` and `Total`, while the components diagnose reconciliation differences ([NAV Summary field reference](https://www.ibkrguides.com/reportingreference/reportguide/net%20asset%20value%20%28nav%29%20summary%20in%20base.htm)). These exact identity, currency and opening-date fields are documented in IBKR’s [Account Information reference](https://ibkrguides.com/reportingreference/reportguide/account%20information%20activity%20flex.htm). Cash Transactions or Statement of Funds should remain a separate diagnostic query because they are unnecessary on every normal page load.

Backfill should begin with **one one-day probe and one controlled seven-day probe**. Activity Flex no longer documents a NAV time-series section, so the seven-day response must prove whether a range produces daily rows or only a period summary. If it contains daily rows, fetch history in non-overlapping chunks of at most 364 days, verify returned boundaries, checksum every raw response and upsert normalized dates. If it returns only one period summary, pull one business day at a time exactly once, skipping checksummed dates and resuming after failure. Run sequentially through a rolling limiter capped below the official ceiling—**at most one HTTP request per second and eight total HTTP requests per minute, including SendRequest, GetStatement and polls**—with backoff for “still generating,” heavy-load and `1018` rate-limit responses. A typical report needs at least two HTTP requests, so report jobs must never be launched at the nominal ten-per-minute request limit. This one-time job can take hours, but the browser never waits for it; afterwards, ingest only the latest closed day plus a small overlap for broker corrections.

The normalized grain should be **one complete reporting day per account and one broker-provided All-in-One consolidated fund row**. For any selected interval, calculate cumulative return as `R = product(1 + r_d) - 1`, where `r_d` is the daily broker TWR; never use `(ending NAV / starting NAV) - 1` across cash flows. Define 1D as the latest complete day, 1W as the latest five complete reporting days, 1M/3M/1YR as trailing calendar intervals anchored to the closest available close on or before the boundary, YTD from the prior year-end close, and ALL from the earliest complete reconciled date. Allocation is `account ending NAV / consolidated ending NAV` on the same date. If IBKR cannot emit a consolidated series, follow IBKR’s method of summing same-day beginning values, ending values and external flows across included accounts and linking the resulting daily fund returns; **never average account return percentages** ([IBKR PortfolioAnalyst return methodology](https://www.ibkrguides.com/portfolioanalyst/pa-white-papers-ie.pdf)). Missing or duplicated days, mixed/unconverted currencies, unresolved flows, newly opened or closed accounts, or an incomplete account population must produce `null` and a quality reason rather than a forward-fill or zero.

The API should return decimal values plus dates and status, not preformatted strings: each period should carry `{value, start_date, end_date, status}`, and the chart should receive daily `{date, cumulative_return}` points for the selected scope. Activity Flex does **not** document benchmark output ([Activity Flex Query reference](https://ibkrguides.com/reportingreference/reportguide/activity%20flex%20query%20reference.htm)). PortfolioAnalyst can compare benchmarks and export performance reports, but no official unattended PortfolioAnalyst Web Service was found ([PortfolioAnalyst account-performance guide](https://www.ibkrguides.com/advisorportal/performanceandstatements/pa_viewingaccountperformance.htm)). Therefore “vs Bench” must wait for an approved, independently licensed **total-return** benchmark series; a price-only close series understates dividends. Store the benchmark identifier, currency, calendar, source and price-versus-total-return type, compound it over the same dates, and calculate `portfolio cumulative TWR - benchmark cumulative total return`.

## Chart.js gives the best chart with least machinery

**Proposed chart.** Use one responsive Chart.js line chart above the account table, with a large selected-period return, compact 1D/1W/1M/3M/YTD/1YR/ALL controls, a zero baseline, fund and benchmark lines, an as-of label, and a hover/focus tooltip showing date and cumulative percentages. Rebase each selected series to 0% at its start and draw cumulative TWR thereafter; changing a period should replace the chart dataset and account return column without rebuilding unrelated table nodes. Use `animation: false`, `parsing: false`, normalized sorted points and the built-in min/max or LTTB decimator only for a dense ALL view. Chart.js explicitly recommends these settings for lower CPU cost and single-pass rendering, and its canvas approach avoids creating a DOM node per historical point ([Chart.js performance guide](https://www.chartjs.org/docs/latest/general/performance.html), [decimation guide](https://www.chartjs.org/docs/latest/configuration/decimation.html)).

The first paint should use the latest valid, compact summary already held in process memory or embedded as a small server-generated payload. Static CSS and JavaScript should use content-hashed filenames with long-lived caching; the sensitive portfolio JSON should remain same-origin and private, with an ETag or a short private cache only if the authentication design supports it. Serve the last good snapshot during ingest, Flex or LSEG failure and label it stale rather than blocking the page. Debounce table search, paginate position detail at 50–100 rows and update only the affected chart or table region. This preserves a polished account-summary-first view while still allowing users to drill into holdings, without shipping hundreds of positions and nearly a thousand tax lots before they ask for them.

## Full portfolio apps add stores and reconciliation

**Software comparison.** Chart.js inside the current FastAPI service is the best immediate fit because it is MIT-licensed, actively maintained and consumes the proposed read-only JSON directly ([Chart.js repository](https://github.com/chartjs/Chart.js)). React-admin with TanStack Table and Recharts is the best later frontend if the product becomes a multi-page application with many resources or account-specific authorization; React-admin’s REST data-provider boundary and independently registered list/show/create/edit views fit FastAPI cleanly ([React-admin](https://github.com/marmelab/react-admin), [TanStack Table](https://github.com/TanStack/table), [Recharts](https://github.com/recharts/recharts)). Grafana is the strongest no-code prototype because its Infinity connector reads JSON and its Viewer role blocks dashboard editing, but a Viewer can still issue arbitrary queries to permitted data sources, so it must receive a deliberately narrow read-only credential and API ([Infinity data source](https://grafana.com/docs/plugins/yesoreyeram-infinity-datasource/latest/query/), [Grafana security guidance](https://grafana.com/docs/grafana/latest/setup-grafana/configure-security/)).

Ghostfolio and Wealthfolio provide attractive portfolio experiences, but neither is a presentation-only shell for an external Flex-derived API. Ghostfolio expects imported activities in PostgreSQL/Redis and exposes transaction writes; Wealthfolio imports activities or snapshots into its own SQLite store and does not document a whole-application Viewer/Editor boundary ([Ghostfolio](https://github.com/ghostfolio/ghostfolio), [Wealthfolio](https://github.com/wealthfolio/wealthfolio), [Wealthfolio import model](https://wealthfolio.app/docs/guide/csv-import/)). Adopting either would create a second canonical portfolio engine whose transfer, dividend, FX, split and return logic must be reconciled forever. Appsmith, Superset and Metabase are credible internal-tool or BI layers, but they add a platform and, for Superset/Metabase, a SQL projection; that cost is unjustified for one fund dashboard. **Do not adopt a full GitHub portfolio UI now.** Trial Grafana only if non-developers need to author dashboards, and revisit React-admin only when the existing page truly becomes a multi-screen product.

Read-only collaboration must be enforced below the UI. The reverse proxy should authenticate each collaborator through institutional SSO/OIDC and map everyone initially to one viewer group; FastAPI should expose no mutation route, no refresh control and no service credential that can write to brokerage, signal or portfolio state. Browser responses should use opaque account keys and display aliases, with raw IDs, Flex tokens, Query IDs and tax-lot details retained only in protected server storage. If later users require different account visibility, enforce that authorization inside FastAPI or through database row security; hiding rows or buttons in JavaScript is not a security boundary.

One documentation mismatch should be fixed during Stage 2. The checked-in ingestion implementation explicitly sends the same one-day value as both `fd` and `td`, while its README says date parameters are omitted and the saved query controls the period; the README also advertises `pull_history`, `rebuild_history` and CSV-export functions that the 166-line implementation does not contain ([ingestion source](https://github.com/SinnQuant/sinnfund-infra/blob/main/services/flex-ingest/flex-ingest.py), [ingestion README](https://github.com/SinnQuant/sinnfund-infra/blob/main/services/flex-ingest/README.md)). Treat the source as current truth, then update code and documentation together when range/backfill support is added.

## Conclusion

The durable product boundary is now clear: IBKR Flex remains immutable evidence, a small daily calculation job becomes the single returns engine, and FastAPI serves an authenticated read-only projection. That boundary makes the dashboard feel immediate, lets every collaborator see identical numbers, and prevents a charting choice from becoming a second accounting system.

The only unresolved product decisions are the approved benchmark, the fund’s historical membership rules when accounts open, close, link or de-link, and whether “ALL” should mean earliest common complete coverage or each account’s own coverage. Those decisions should be recorded before publishing comparative or since-inception numbers; they do not block the immediate cached account summary or the initial Chart.js implementation.
