# Current UI and backend architecture for a read-only portfolio platform

## Is the current delay an animation, and what work happens before and after first paint?

### Takeaway
There is no animation in either portfolio dashboard. A request waits for the latest compressed Flex report to be found, decompressed, parsed, serialized into a large inline JSON payload, and—on the live page—repriced through two sequential localhost calls; the browser then synchronously parses that payload and rebuilds the full positions table. The deployed server-side path is currently quick, so the most visible handling cost is likely the large response and full DOM rebuild rather than an intentional animation.

### Cited Findings
- Neither dashboard contains CSS animation/transition rules, `requestAnimationFrame`, delayed timers, or a loading animation. Both contain a single synchronous `render()` call after parsing the embedded JSON. — [close dashboard](file:///Users/enoch/sinnfund-infra/services/flex-web/web.py#L31); [live dashboard](file:///Users/enoch/sinnfund-infra/services/flex-web-live/web-live.py#L55)
- `GET /` calls `load_report()` before returning any HTML. `load_report()` finds the newest archive directory, opens every `*.xml.gz`, parses positions and lots, and the route then serializes all results into an inline `<script type="application/json">`. Nothing can paint in the browser until this finishes and the response begins. — [close request path](file:///Users/enoch/sinnfund-infra/services/flex-web/web.py#L249); [close parser](file:///Users/enoch/sinnfund-infra/services/flex-web/parse_flex_positions.py#L64)
- The live parser performs one blocking `GET http://127.0.0.1:8091/prices` with a five-second timeout after parsing the XML. `load_report()` then performs a separate blocking health request with another five-second timeout. These are sequential, so a degraded price service can add roughly ten seconds before HTML is returned even though the parser falls back to Flex marks. — [live price request](file:///Users/enoch/sinnfund-infra/services/flex-web-live/parse_flex_positions_live.py#L139); [live health request and load order](file:///Users/enoch/sinnfund-infra/services/flex-web-live/web-live.py#L37)
- Every response is marked `Cache-Control: no-store`; there is no process cache, derived report file, ETag, conditional response, or static asset cache. The same XML parsing and JSON serialization repeat for every user and refresh. — [close headers and route](file:///Users/enoch/sinnfund-infra/services/flex-web/web.py#L261); [live headers and route](file:///Users/enoch/sinnfund-infra/services/flex-web-live/web-live.py#L318)
- Browser initialization builds a tax-lot map from every lot, constructs every visible table cell, and attaches handlers row by row. Search runs `render()` on every input event; sorting, account changes, and expanding one row all clear and rebuild the full table. — [close browser render](file:///Users/enoch/sinnfund-infra/services/flex-web/web.py#L113); [live browser render](file:///Users/enoch/sinnfund-infra/services/flex-web-live/web-live.py#L140)
- A read-only production measurement on 2026-11-06 found one latest archive containing 403 summary positions and 943 lots across 21 accounts. The uncompressed XML was about 1.64 MB; the generated close and live HTML responses were about 835 KB and 925 KB. Five localhost requests produced 60–86 ms close TTFB and 93–127 ms live TTFB. — [deployed close application](ssh://sinnfund/opt/flex-web/web.py); [deployed live application](ssh://sinnfund/opt/flex-web-live/web-live.py); [deployed archive](ssh://sinnfund/var/lib/flex-ingest/flex/data/20261105/)
- The user’s reference table is an account-level view with roughly 20 rows, aliases, NAV, allocation, YTD return, and benchmark comparison. The current dashboards instead lead with 403 position rows and include 943 tax lots in the initial payload, even though most are not needed for that first screen. — [reference image](file:///var/folders/5j/8x8xvxqd38g0zg0s85jqhzvr0000gn/T/codex-clipboard-14c7c57d-1ce5-4c9d-8352-88753ec76a08.png); [current columns](file:///Users/enoch/sinnfund-infra/services/flex-web/web.py#L136)

### Inferences
- The user may be describing the blank wait before the response and the table’s full redraw as an “animation.” No animation can be optimized because none exists in the checked code.
- On the current host, request-time parsing is wasteful but not yet the dominant steady-state latency. Network transfer, JSON parse, thousands of DOM nodes, and full rerenders will become more noticeable on slower devices and with more users.
- The live page has a poor tail-latency mode: it normally returns in about a tenth of a second, but a stalled local price API can hold the first byte for several seconds.
- A 21-row account summary is a materially better first payload for the requested product than the current full position/lot document.

### Gaps
- No browser performance trace, device profile, public-route timing, Nginx compression setting, or video of the reported animation was available. The exact user-visible bottleneck therefore remains unmeasured.
- There are no Flex dashboard tests or performance budgets in this repository, so regressions in response size, first paint, and interaction latency are currently unchecked.
- The repository does not contain the Stage 4 risk UI referenced by the ADRs, so this audit covers only `flex-web`, `flex-web-live`, and their ingestion path.

## What is the smallest complete immediate-load, multi-user, read-only design?

### Takeaway
Keep the existing FastAPI service and immutable raw Flex archives. Build one small, atomic, derived account-summary artifact after ingestion, serve it from memory or disk without touching XML or LSEG during a page request, and fetch positions/lots only when a user opens an account. This removes the blank request-time work and makes the first meaningful screen about 21 account rows rather than hundreds of positions.

### Cited Findings
- Raw compressed Flex XML is already the accepted immutable source of truth, and projections are meant to be downstream and reproducible. A derived summary cache fits that boundary without replacing or modifying evidence. — [ADR-0007](file:///Users/enoch/sinnfund-infra/docs/decisions/0007-archive-raw-flex-xml.md)
- The existing architecture explicitly chooses a centrally maintained, read-only-first service with dated snapshots, quality status, reconciliation, access control, and operational handoff. — [ADR-0001](file:///Users/enoch/sinnfund-infra/docs/decisions/0001-stakeholder-driven-read-only-platform.md)
- Existing reporting surfaces are required to remain read-only and separate from trade controls; credentials and internal history services should stay outside public Nginx exposure. — [ADR-0005](file:///Users/enoch/sinnfund-infra/docs/decisions/0005-separate-public-read-only-and-private-controls.md)
- The current applications already bind Uvicorn to loopback and rely on an authenticated reverse proxy because they have no application authentication. — [close service](file:///Users/enoch/sinnfund-infra/services/flex-web/deploy/flex-web.service); [live service](file:///Users/enoch/sinnfund-infra/services/flex-web-live/deploy/flex-web-live.service); [close security note](file:///Users/enoch/sinnfund-infra/services/flex-web/web.py#L13)
- The existing risk-dashboard decision follows the same useful pattern: do calculation outside HTTP requests and make the website a read-only adapter over versioned artifacts so temporary upstream outages do not block reporting. — [ADR-0019](file:///Users/enoch/sinnfund-infra/docs/decisions/0019-read-only-stage4-over-stage3-artifacts.md)

### Inferences
- Smallest backend change:
  1. After a successful daily Flex ingest, run a builder that writes `portfolio-summary.json` to a temporary file and atomically renames it. Preserve source date, checksums, generated time, query/schema version, and quality status.
  2. Load the latest valid summary at application startup and swap it only after a complete new artifact validates. Continue serving the last good snapshot with an explicit stale badge if ingestion or quote refresh fails.
  3. Make `GET /api/v1/portfolio?as_of=latest` return only fund totals and account rows. Keep the HTML/CSS/JS shell static and cacheable; keep sensitive JSON `private, no-store` or use short private caching plus ETags according to the authentication design.
  4. Add `GET /api/v1/accounts/{opaque_account_key}/positions?as_of=...` and return lots only when that account/position is expanded. Do not embed all raw account IDs and tax lots in the initial document.
- A compact first response should contain `as_of`, `generated_at`, `data_status`, fund NAV/allocation totals, and approximately 21 account records with name, opaque account key, NAV, allocation, seven returns, coverage start, and per-row quality status. This directly matches the reference table.
- Client-side changes can stay small: render the account table immediately; debounce search; update only the changed header/body or use a `DocumentFragment`; paginate position detail to 50–100 rows. A framework, WebSocket, canvas table, animation library, and managed database are unnecessary at this scale.
- Static CSS/JS can use content-hashed filenames with long browser caching. Keeping data separate means a new snapshot does not resend application code, and a code deploy does not duplicate the full data payload.
- For multiple collaborators, one authenticated URL with institutional SSO/OIDC at Nginx (or an auth proxy) and a single viewer group is sufficient initially. Expose only `GET`, `HEAD`, and health routes; do not add comments, edits, refresh controls, token input, or account mutations while the product is read-only.
- Server-side caching should be keyed by source archive checksum/date and, for the delayed-price view, the LSEG snapshot identifier. A last-good artifact is preferable to request-time LSEG calls because upstream slowness should change freshness labels, not block first paint.

### Gaps
- Current Nginx authentication, authorization groups, TLS policy, compression, and cache configuration were not present in the audited repository.
- “Collaborate” may later mean comments, annotations, or shared watchlists. Those are write features and are intentionally outside this read-only first phase.
- Account alias ownership and which account identifiers may be shown to each viewer need a data-owner decision before the summary API contract is finalized.

## Can the existing Flex and LSEG data produce 1D, 1W, 1M, 3M, YTD, 1YR, and ALL returns, and what schema and rules are required?

### Takeaway
The Flex credential can retrieve the necessary reporting data, but the token does not calculate returns and the current saved query does not request enough fields. The deployed archives have cash-flow fields but their NAV-summary rows contain only `accountId`, so they cannot support defensible portfolio returns. Add NAV and Change-in-NAV/TWR fields to a dedicated saved Flex query, perform one bounded historical backfill in ranges of up to 365 days, store daily broker TWR/NAV by account and consolidated fund, and compound the daily TWR for the seven UI periods.

### Cited Findings
- The current ingestion code sends one-day `fd`/`td` overrides and archives the raw response. It does not parse or persist NAV or performance returns. — [current ingestion](file:///Users/enoch/sinnfund-infra/services/flex-ingest/flex-ingest.py#L80)
- The production archive spans only 19 dated folders from 2026-10-09 through 2026-11-05. Its latest `EquitySummaryByReportDateInBase` records contain only `accountId`; they omit report date, total NAV, and TWR. `CashReportCurrency` includes deposits, withdrawals, transfers, starting cash, and ending cash, but cash is not total portfolio NAV. — [deployed archives](ssh://sinnfund/var/lib/flex-ingest/flex/data/); [current query output](ssh://sinnfund/var/lib/flex-ingest/flex/data/20261105/main.xml.gz)
- The accepted accounting design forbids inferring account NAV from cash or gross securities exposure and requires official source fields; prior work found NAV/base-currency information incomplete. — [ADR-0013](file:///Users/enoch/sinnfund-infra/docs/decisions/0013-audit-flex-accounting-before-var.md); [ADR-0018](file:///Users/enoch/sinnfund-infra/docs/decisions/0018-publish-dollar-risk-without-nav.md)
- IBKR’s Activity Flex Query supports both **Change in NAV** and **Net Asset Value (NAV) Summary in Base**. Change in NAV can include starting NAV, ending NAV, deposits/withdrawals, asset and internal transfers, income/fees, and broker-calculated TWR; IBKR defines TWR as return independent of contribution and withdrawal timing. — [IBKR Activity Flex Query reference](https://ibkrguides.com/reportingreference/reportguide/activity%20flex%20query%20reference.htm); [IBKR Change in NAV fields](https://ibkrguides.com/reportingreference/reportguide/changeinnav_fq.htm); [IBKR NAV summary fields](https://www.ibkrguides.com/reportingreference/reportguide/net%20asset%20value%20%28nav%29%20summary%20in%20base.htm)
- IBKR Flex Web Service allows `fd`/`td` overrides of up to 365 days, so historical data should be requested in annual chunks rather than one request per day. The service limits a token to one request per second and ten requests per minute. — [IBKR Flex Web Service configuration](https://ibkrguides.com/orgportal/performanceandstatements/flex3.htm); [IBKR error and rate-limit reference](https://www.ibkrguides.com/adminportal/performanceandstatements/flex3error.htm)
- IBKR states saved Flex queries are available for the four prior calendar years plus the current year, which may cover the reference account that says it began in February 2023 but is not an unlimited lifetime archive. — [IBKR Flex Queries](https://ibkrguides.com/clientportal/performanceandstatements/flex.htm); [reference image](file:///var/folders/5j/8x8xvxqd38g0zg0s85jqhzvr0000gn/T/codex-clipboard-14c7c57d-1ce5-4c9d-8352-88753ec76a08.png)
- The host’s separate LSEG history component stores per-symbol daily adjusted `TRDPRC_1` in SQLite and is designed for instrument-market history, not realized account performance. Its own documentation warns that FX, cash flows/dividends, splits, and coverage checks remain necessary. Market returns from current holdings cannot substitute for historical fund returns. — [deployed LSEG history README](ssh://sinnfund/opt/lseg-history/README.md); [ADR-0012](file:///Users/enoch/sinnfund-infra/docs/decisions/0012-lseg-history-private-sqlite-cache.md); [ADR-0020](file:///Users/enoch/sinnfund-infra/docs/decisions/0020-dated-risk-snapshots-vs-price-history.md)
- The LSEG history refresh timer is active, but its local HTTP API was not listening on port 8092 during the 2026-11-06 check. This does not block a Flex-based account-return series, but it prevents treating that API as a currently available dashboard dependency. — [deployed refresh timer](ssh://sinnfund/etc/systemd/system/lseg-history-refresh.timer); [deployed history API](ssh://sinnfund/opt/lseg-history/history_api.py)
- The checked-in Flex ingestion README describes historical functions (`pull_history`, `rebuild_history`, CSV exports) that do not exist in the checked-in 166-line implementation. The source code, not that README, is the current capability. — [ingestion README](file:///Users/enoch/sinnfund-infra/services/flex-ingest/README.md#L13); [ingestion source](file:///Users/enoch/sinnfund-infra/services/flex-ingest/flex-ingest.py)

### Inferences
- Create a dedicated read-only performance query instead of changing the positions query in place. Include account alias, base currency, report date, NAV total, starting/ending NAV, external flows/transfers, and broker TWR. Request both account-by-account and consolidated/fund output if IBKR supports the account configuration; broker-calculated consolidated TWR is preferable to an approximation across accounts.
- Bootstrap history once in at most 365-day chunks, throttle below IBKR’s published limit, save every raw response with a unique range/query-schema name, checksum it, and make the import idempotent. Do not overwrite the existing daily position evidence. After backfill, the daily timer only needs the latest closed day plus a small overlap for corrections.
- Suggested minimal SQLite schema (SQLite is already the host precedent and sufficient for this scale):
  - `performance_snapshot(scope_key, account_key, date, nav_base, base_currency, external_flow, twr_daily, source_file, source_checksum, source_query_version, quality_status, imported_at)` with a unique key on `(scope_key, account_key, date)`.
  - `account(account_key, display_name, source_account_hash, active_from, active_to)`; keep raw brokerage IDs in protected storage and send an opaque key/display alias to browsers.
  - `source_import(source_checksum, query_version, from_date, to_date, fetched_at, status, error)` for idempotence and auditability.
- Period-return rule: use daily broker TWR and calculate `product(1 + r_day) - 1` over the selected complete dates. Never calculate performance as `(ending NAV / starting NAV) - 1` when deposits, withdrawals, transfers, account links, or asset transfers occurred.
- Date semantics should be fixed and shown in the API/UI:
  - `1D`: latest complete reporting day.
  - `1W`: last five complete market/reporting days.
  - `1M`, `3M`, `1YR`: trailing calendar month(s)/year, starting at the closest available date on or before the boundary.
  - `YTD`: from the last complete NAV of the prior calendar year through the latest complete date.
  - `ALL`: from the first date with complete, reconciled coverage; label it “since <date>,” because Flex retention may truncate true inception.
- If any daily account is missing, duplicated, in a different/unconverted base currency, or has an unresolved external flow, return `null` plus a quality reason for affected periods rather than forward-filling or treating missing returns as zero. New accounts should show shorter coverage instead of an invented pre-opening history.
- For fund return, prefer a broker-provided consolidated TWR series. If unavailable, calculate each day from complete same-currency account series using beginning-NAV weights, document the method, and reconcile it against IBKR before publication. Allocation is `account ending NAV / consolidated ending NAV` only after that reconciliation.
- A benchmark comparison needs its own total-return series and declared benchmark (for example, an approved total-return index). Price-only LSEG closes can understate dividends and must be labeled accordingly; “vs Bench” should be `portfolio TWR - benchmark total return` over the exact same dates.
- The summary API should return decimals/nulls and explicit quality metadata rather than formatted strings: `{value, start_date, end_date, status}` for each period makes stale or incomplete rows visible and testable.
- Validation/security checks before release: reconcile daily NAV totals and TWR to an IBKR statement sample; verify cash-flow classification, linked/de-linked accounts, base currency and FX conversion, inception/closed accounts, duplicate statements across books, revised broker history, and corporate actions. Protect raw IDs and tax lots, do not put Flex/LSEG credentials in browser code, enforce viewer authentication at the proxy, log access without sensitive query strings, and confirm account-data and LSEG redistribution permissions.

### Gaps
- The token itself was not printed or directly exercised. A fresh 2026-11-05 archive and active timer show that the deployed token/query recently retrieved data, but token expiry and permission for a new performance query still require a bounded smoke test.
- The exact IBKR multi-account delivery mode and whether consolidated TWR is available for this master-account structure must be confirmed in Client Portal.
- The LSEG SQLite row coverage could not be inspected with the connected SSH user because the database is correctly restricted to the service account; it is unnecessary for the account-return design but remains a gap for benchmark selection.
- “ALL” cannot be promised as true since-inception until the earliest account dates are compared with IBKR’s available retention and any older statements/backups.
